# Legacy salvage review

This review decides which **user value**, if any, survives the Java repository.
It is deliberately stricter than the artifact inventory. A controller, table,
page, test class, or manual proves that an idea existed; none of those alone
prove that the behavior is valuable, safe, complete, or suitable for reuse.

The decisions mean:

- `CORE_REQUIREMENT_ONLY`: preserve only a narrow, demonstrated user
  requirement. No Java implementation, schema, identifier, or stored record is
  reused.
- `CORE_REBUILD_FROM_ZERO`: the need belongs in the first Go release, but the
  Java design, source, schema, protocols, and failure behavior are rejected.
- `LATER_FROM_ZERO`: omit the capability, route, schema, background job, and UI
  from the first release. A later independently accepted vertical slice may
  start from requirements and evidence, not from the Java implementation.
- `DROP`: neither implementation nor product surface enters the Go product.

`First release=YES` means the capability may appear only after its CORE
acceptance rows pass. `NO` and `DROP` are not core release blockers.
Static UI is treated only as workflow-intent evidence. Repository tests are
called closed-loop only when they exercise the real persistence, process,
network, crash, schema-upgrade, and browser boundaries; the reviewed Java tests do
not establish that level for any feature below.

## Consequence for the first Go release

The first release is intentionally a lean vertical slice: a secure local session
opens one Vault; the user uploads supported documents, organizes true M:N
collections, searches with controlled SQLite FTS, asks with honest refusal or
limitation labels and supplied-source citations through explicitly configured loopback Ollama,
keeps conversation provenance, trashes or truthfully purges data, and can back
up, restore, and upgrade that Vault across supported Go schema versions.
Everything marked `LATER_FROM_ZERO` must be
absent rather than shipped as a disabled or half-wired legacy port.
